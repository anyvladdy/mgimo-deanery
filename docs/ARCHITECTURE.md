# Карта приложения

Один сервер принимает запросы, читает одну SQLite-базу и отдаёт HTML. Папки названы по делам студента. Так задачу «починить ведомость» можно целиком открыть в одном месте. Общих технических частей три — запуск сервера, база и оформление.

### Контракт веб-модулей после этапа 1

Точка сборки — `src/server.js`. Вход и выход лежат в `src/account/routes.js`, состояние сессии — в `src/account/sessions.js`. Пароли проверяются через scrypt с отдельной солью. Подписанная cookie содержит случайный идентификатор. Сервер хранит его хеш, ссылку на студента, токен формы и срок сессии. Успешный вход заменяет гостевую сессию, выход удаляет её на сервере.

- Новый модуль экспортирует функцию, например `requestRoutes(db)`, которая возвращает `new Hono()`. В `module.js` функция `studentMount` возвращает `['/requests', requestRoutes(db)]`. Сервер монтирует её после проверки студенческой сессии. Внутри модуля путь списка — `/`.
- Идентификатор текущего студента — `c.get('studentId')`. Для изменений используй POST с обычным HTML form. Скрытое поле `_csrf` получает значение `c.get('csrfToken')`. Общая проверка формы выполняется до обработчика, проверенные на CSRF поля доступны через `c.get('form')`. Содержимое полей валидирует сам модуль.
- Учётная запись сотрудника находится в `staff_accounts`, привязка к проверенной сессии — в `staff_sessions`. `c.get('staff')` получает актуальную роль из базы. `/office` защищён отдельным шлюзом, преподаватель видит назначенные ведомости и диалоги, в которых он получатель. Выход отзывает обе связанные записи сессии.
- Серверные шаблоны импортируют `html` из `hono/html` и оборачивают содержимое через `layout(title, content, { student, csrf, active })` из `src/ui/layout.js`. После `requireStudent` сервер загружает `c.get('student')`; передавай его и `csrfToken` в страницы, чтобы шапка показывала навигацию и выход. Возвращай результат через `c.html(...)`. Образец — `src/account/pages.js`.
- Базовые контракты находятся в `src/requests/schema.sql`, `src/grades/schema.sql` и `src/notices/schema.sql`: `document_requests(id, student_id, kind, status, created_at)`, `grades(id, student_id, subject, assessment, result, exam_date)`, `notices(id, group_code, kind, message, notice_date)`. Заполнение этих таблиц относится к этапам соответствующих функций. Для личных записей включай `student_id` в сам запрос.
- Для теста используй `createApp(db, { secret, secure })` и `app.request(...)`. Образец двух независимых cookie — `tests/account.test.js`. Команда локального запуска и доступы есть в [README](../README.md).

| `GET /urgent-appeals`, `POST /urgent-appeals`, `GET /urgent-appeals/:id` | Студент | Отправка срочного обращения и личный статус. Параметр `request` привязывает собственную заявку. |
| `GET /office/urgent-appeals`, `GET /office/urgent-appeals/:id`, `POST /office/urgent-appeals/:id/handle` | Назначенный получатель | Ответ или передача с уровня программы на уровень факультета, затем в ректорат. |
| `GET /office/urgent-appeals/routing`, `POST /office/urgent-appeals/routing` | Администратор | Назначение получателя на одну программу, факультет или ректорат. |
| `GET /services/in-development` | Студент | Описание планируемых СОП и «Благодарностей и предложений». |

`assignments` хранит опубликованные задания. `assignment_submissions` связывает задание и студента, текст и ссылку, номер редакции, статус и комментарий. После перевода историческая работа остаётся доступна автору, а сдача проверяет актуальную группу. Повтор отправки с тем же содержанием сохраняет текущую редакцию. Возврат на доработку разрешает новую попытку после первоначального срока.

`university_news` хранит публикации. Ссылка на событие проходит через проверку модуля кампуса. `urgent_appeals` связывает студента, номер его заявки при наличии, снимок программы и факультета и уровень получателя. `urgent_recipients` назначает конкретного сотрудника на область маршрутизации. `urgent_appeal_events` хранит передачу и ответ. Номер версии защищает от повторного перевода устаревшей формы. Совместимый с прежними файлами SQLite тип `leadership` в `staff_accounts.role` открывает только очередь срочных обращений. Администратор управляет назначениями, а детали читает только назначенный получатель.

Новые таблицы создаются при открытии SQLite. Существующие записи и структура прежних таблиц сохраняются. Демо-задание и новость добавляются через демоданные при следующем запуске.

### Как восстанавливается доступ

Форма `/recover` принимает логин и даёт одинаковый ответ для любого корректно заполненного поля. `student_password_resets` хранит запросы существующих студенческих аккаунтов. Для каждого аккаунта одновременно действует один запрос на рассмотрении или один выданный код. В `/office/recovery` сотрудники с ролями `office` и `admin` принимают решение после проверки личности вне кабинета. Одобренный код действует 30 минут. В SQLite хранится его хеш, сам код виден на экране выдачи.

Смена пароля проходит в транзакции. Код погашается, в `accounts` записывается новый хеш с новой солью, прежние сессии студента удаляются. Вход проверяет актуальность хеша в момент выдачи новой сессии. После изменения ФИО `students.full_name` читают профиль и реестр. Условие записи проверяет, совпадает ли текущее имя со значением, показанным при открытии редактора.

### Как хранятся сообщения

`message_threads` связывает тему, студента и канал обращения. Для личного диалога сервер проверяет, что преподаватель активен и назначен группе студента. После создания история доступна участникам по их идентификаторам. При отключении аккаунта преподавателя студент может просмотреть диалог и открыть новое обращение в офис. Учебный офис и администратор видят только учебные и технические обращения.

`thread_messages` хранит автора, текст и время. Первое сообщение и тема создаются в одной транзакции. Идентификатор отправки в форме защищает от дублирования. Общие шлюзы проверяют сессию и CSRF. При каждом чтении и записи проверяется доступ к конкретному диалогу. HTML экранируется через `hono/html`.

Таблицы и индексы добавляются штатным `openDatabase` при следующем запуске. Преобразования существующих строк нет. При возврате к прежнему коду таблицы переписки остаются на диске.

Ссылки из пары, силлабуса и заявки передают ссылочный идентификатор в `/messages/new`. Получателя и тему форма подставляет из проверенной записи. Назначение преподавателя проверяется по группе, заявку выбирают по владельцу. Ответ сотрудника попадает в личную ленту и ведёт к якорю конкретного сообщения. Прочтение в `message_reply_reads` хранится отдельно от состояния обращения.

`message_cases` содержит ответственного и дату закрытия учебных и технических обращений. Сотрудник может взять свободное обращение, первый ответ тоже закрепляет ответственного. Ответственный или администратор закрывает обращение, если последнее сообщение от офиса. Новый текст от студента возвращает обращение в очередь вместе с историей.

### Расписание экзамена

Офис публикует версию даты, времени по Москве, корпуса и аудитории в `exam_slots` для группы и дисциплины с экзаменом в ожидании результата. Студент видит текущую версию только для своей группы и доступной строки ведомости. Лента сравнивает текущую версию с предыдущей или с прежней датой из ведомости при первой публикации. `exam_slot_reads` отмечает каждую версию отдельно. У существующих экзаменов с одной датой работает прежнее напоминание. Устаревшая форма редактора возвращает 409, повтор с теми же данными сохраняет опубликованную версию.

### Один перенос от записи до трёх экранов

1. Исходная аудитория лежит в `lessons.scheduled_room`. Запись `room_changes` связывает занятие с новой аудиторией. Для объёма этих двух дней у пары может быть один перенос кабинета.
2. Представление `student_schedule` подбирает пары по группе студента и вычисляет текущую аудиторию. Перенос попадает на главную, в расписание и уведомления из одной записи. У обычной пары текущая аудитория совпадает с исходной.
3. Прочтение добавляет ключ «студент + перенос» в `change_reads`. Главная отфильтровывает прочитанное. Недельное расписание сохраняет обе аудитории. Из интерфейса личность передаёт серверная сессия.
4. Чтобы изменить учебный пример, отредактируй `src/schedule/seed.sql`. Чтобы изменить правило видимости, открой `src/schedule/schedule.js` и запусти `npm test`. Чтобы изменить подпись «было», на веб-этапе меняй общий фрагмент переноса в `src/schedule/`.

Схему и её применение к существующему файлу базы меняет интегратор. При добавлении этапа проверь и чистый запуск, и перезапуск с уже сохранённой заявкой. Загрузка учебных данных запускается отдельно от старта сервера.

Новые таблицы D38–D41 добавляются при открытии SQLite. Данные старых таблиц и действующие студенческие сессии сохраняются. Для отката версии приложения можно запустить предыдущий код поверх той же базы. Записи новых таблиц останутся доступными после повторного обновления.

Таблицы D42–D43 добавляются тем же способом. Начальные программы и группы заполняются из согласованных существующих записей студентов. Публикация использует отдельный слой версий и удерживает справочные строки для ссылок из ведомостей.

### Срез D47–D49

- **Перевод.** `moveStudent` удаляет выборы блоков, которых нет у новой группы, и пишет `plan_choice_history`; места снова свободны, призрачная дисциплина не остаётся в плане.
- **Пересдача.** Состав берётся из опубликованной основной ведомости, а при её отсутствии — из текущей группы и `student_retained_courses`. Переведённый студент с долгом остаётся в пересдаче, пока долг не закрыт.
- **Публикация плана.** Удаление дисциплины блокируется, если по ней есть открытая ведомость или непогашенный долг (включая переведённых студентов).
- **Формы.** Некорректный multipart и ошибка разбора дают 400; CSRF сравнивается по байтовой длине; CSS получает общие заголовки; HSTS и Referrer-Policy включены.
- **Лимит входа.** Десять неверных попыток на логин блокируются на десять минут; успешный вход сбрасывает счётчик. Это локальная защита, не замена прокси.
- **Мобильный экран.** Шапка на 320–390 px показывает все разделы сеткой 3×2 или 2×3; контраст границ контролов 3,47:1; сводки не ломаются по буквам; выбранный день не дублируется в неделе.
